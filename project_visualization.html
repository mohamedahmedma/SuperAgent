Project Overview

SuperMew is an advanced intelligent Q&A knowledge-base system built around the Self-Reflective RAG (CRAG) concept. It breaks past the limits of traditional, simple RAG (bare similarity recall handed straight to the model) with a substantial amount of industrial-grade engineering aimed at recall quality, context completeness, and hallucination prevention.

FastAPI LangChain LangGraph (state machine orchestration) Milvus (dual-path vector database) HuggingFace (local embeddings)

🌟 Six Core Engineering Highlights

  • LangGraph autonomous retrieval correction: if the initial retrieval relevance is poor, the system automatically triggers a Step-back question or HyDE (hypothetical document) generation to expand the query.
  • Dual-path hybrid retrieval engine: rather than relying on a commercial API, the system hand-implements persistent BM25 sparse vector computation in embedding.py. Combined with dense semantic vectors, it uses the RRF (Reciprocal Rank Fusion) algorithm in Milvus to fuse rankings, balancing semantic generalization with precise proper-noun matching.
  • Parent-Child Chunking: to solve retrieval fragmentation, the system splits documents into three tiers (L1/L2/L3). Only the tiny L3 chunks go into Milvus; once one is matched, the system automatically traces back up to pull the larger L2/L1 context for the LLM.
  • Anti-hallucination system prompt: strictly constrains the Agent to answer only from knowledge-base results, forbidding forced answers with no evidence or getting stuck in a lookup loop within a single turn.
  • High-concurrency streaming pass-through: since the full RAG flow is time-consuming, the system uses asyncio.Queue in agent.py to capture the underlying engine state in real time, pushing "retrieval progress" to the frontend before the LLM even starts thinking.
  • Lightweight, low-dependency architecture: aside from underlying libraries, the core algorithms are largely hand-written natively (e.g. the BM25 incremental state machine, the native SSE protocol handling), keeping everything highly transparent and controllable.

🧠 [Highlight] AI Brain State Machine Orchestration (backend/rag_pipeline.py)

A typical RAG flow is linear: "search -> assemble prompt -> LLM output". But real-world document search often fails (e.g. the user uses a synonym, or the reference is ambiguous). This system uses LangGraph to build a cyclic state graph with a self-correction mechanism (Self-Reflective RAG).

Core Mechanism 1: The Document Judge (Grader)

After the initial retrieval (retrieve_initial), the system doesn't rush the main model into answering — it first has a small model (the Grader) "score" the results. If the documents are completely off-topic, they're immediately marked no, preventing the main model from hallucinating.

Core Mechanism 2: Query Transformation

After being rejected by the Grader, the system enters rewrite_question_node. This isn't simple word-swapping — it uses a more advanced strategy:

  • HyDE (Hypothetical Document Embeddings): when the question is very conceptual, the model is asked to "blind-answer" by writing a hypothetical article, and that article's vector is used for the search. Because the writing style of an answer tends to be closer to the original documents, the similarity match is much stronger.
  • Step-back: if the question is a specific "error log" lookup, the system steps back and asks "what is the troubleshooting principle for this component," which recalls the broader structural documentation.

Core Code Walkthrough: LangGraph Directed Graph Compilation

This snippet defines the entire lifecycle of the AI's reasoning:

def build_rag_graph():
    # 1. RAGState is the shared memory flowing through the graph, holding the question, documents, and trace
    graph = StateGraph(RAGState)

    # 2. Register graph nodes (define the execution functions)
    graph.add_node("retrieve_initial", retrieve_initial)
    graph.add_node("grade_documents", grade_documents_node)
    graph.add_node("rewrite_question", rewrite_question_node)
    graph.add_node("retrieve_expanded", retrieve_expanded)

    # 3. Lay out the fixed single-track path
    graph.set_entry_point("retrieve_initial")
    graph.add_edge("retrieve_initial", "grade_documents")

    # 4. [The soul of it] Conditional branch: decide the route based on the grader's score
    graph.add_conditional_edges(
        "grade_documents",
        lambda state: state.get("route"),
        {
            "generate_answer": END, # Passed grading: end graph execution, the main model is ready to answer
            "rewrite_question": "rewrite_question", # Failed grading: go rewrite the question
        },
    )

    # 5. Once rewritten, run the second search, then finish
    graph.add_edge("rewrite_question", "retrieve_expanded")
    graph.add_edge("retrieve_expanded", END)

    return graph.compile()

🔢 [Highlight] Local Incremental BM25 Sparse Vectors (backend/embedding.py)

The vectors produced by commercial embedding models (e.g. OpenAI, BAAI) are called "dense vectors," and they're great at "fuzzy semantic matching." But search a manual for "model XYZ-9988C" and dense vectors often fail completely. This is where the system hand-writes a BM25 (sparse) vector algorithm in pure Python.

Hardcore Detail 1: A self-contained state machine with no external dependency

The system doesn't rely on an external ElasticSearch — instead it maintains a data/bm25_state.json file. Every time a document is uploaded or deleted, it's safely locked (threading.Lock()) and each term's doc_freq (inverse document frequency) and the corpus-wide total_docs are recomputed, implementing a lightweight incremental IDF.

Core Code Walkthrough: Building the TF-IDF Sparse Vector

Because of Milvus's SPARSE_INVERTED_INDEX requirements, we need to convert text into a dictionary shaped like {term ID: score} (containing only non-zero scores — that's what makes it "sparse").

def _sparse_vector_for_text_unlocked(self, text: str):
    # 1. Tokenize and count term frequency (TF) for this sentence
    tokens = self.tokenize(text)
    doc_len = len(tokens)
    tf = Counter(tokens)

    sparse_vector = {}
    for token, freq in tf.items():
        # Vocabulary index, used to give Milvus an inverted-index ID
        idx = self._vocab[token]

        # 2. IDF calculation (inverse document frequency): terms too common across the corpus get heavily penalized
        df = self._doc_freq.get(token, 0)
        if df == 0:
            idf = math.log((n + 1) / 1)
        else:
            idf = math.log((n - df + 0.5) / (df + 0.5) + 1)

        # 3. The classic BM25 formula
        # numerator: caps TF growth (saturation parameter k1)
        # denominator: introduces the document-length penalty (parameter b)
        numerator = freq * (self.k1 + 1)
        denominator = freq + self.k1 * (1 - self.b + self.b * doc_len / avg)

        score = idf * numerator / denominator
        if score > 0:
            # { dimension ID: score } — this is the essence of a sparse vector
            sparse_vector[idx] = float(score)

    return sparse_vector, vocab_changed

Core Code Walkthrough: The RRF (Reciprocal Rank Fusion) Algorithm

This is the hardest step in hybrid retrieval: Dense distance scores (e.g. 0.81) and BM25 scores (e.g. 25.4) are like apples and oranges — you can't just take a weighted average. The system cleverly uses the RRF algorithm, which completely discards absolute scores and merges results using only each side's rank order.

def hybrid_retrieve(self, dense_embedding, sparse_embedding, top_k=5):
    # 1. Build the semantic query: fetch extra candidates (top_k * 2) to feed the fusion below
    dense_search = AnnSearchRequest(
        data=[dense_embedding], anns_field="dense_embedding", limit=top_k * 2
    )

    # 2. Build the pure keyword/term-frequency query
    sparse_search = AnnSearchRequest(
        data=[sparse_embedding], anns_field="sparse_embedding", limit=top_k * 2
    )

    # 3. Set up the RRF reranker (rerank score = 1 / (k parameter + per-path rank))
    # The higher the rank (the smaller the per-path rank number), the higher the score; ranking high on both paths gives a big boost
    reranker = RRFRanker(k=60)

    # 4. Hand both concurrent search paths off to Milvus and get back the sorted results
    results = self.client.hybrid_search(
        collection_name=self.collection_name,
        reqs=[dense_search, sparse_search], # Multi-path concurrency
        ranker=reranker,                    # Use RRF to combine scores
        limit=top_k
    )
    return results

📄 [Highlight] Parent-Child Document Chunking (backend/document_loader.py)

The system uses "three-tier chunking" to solve RAG's perennial pain point: chunk too small (high hit rate, but the model can't understand the context), chunk too large (matching a whole page floods retrieval with noise).

Chunking Strategy & Storage Separation

Documents pass through a sliding-window RecursiveCharacterTextSplitter and become three tiers. But the cleverest part is: only the smallest fragments (L3) ever go into Milvus — the larger chunks (L1/L2) are stored purely as local JSON, carrying only a lineage ID (parent_chunk_id). Once a highly precise L3 chunk is matched, the system uses that ID to pull up the dormant, larger L1 passage for the model to understand.

Core Code Walkthrough: Lineage-Cascaded Splitting

class DocumentLoader:
    def _split_page_to_three_levels(self, text, base_doc):
        # [Level 1 - macro tier] Large sections of roughly 1200 characters
        level_1_docs = self._splitter_level_1.create_documents([text])
        for l1_doc in level_1_docs:
            l1_id = self._build_chunk_id(1) # Issue L1 its unique ID

            # [Level 2 - meso tier] Split the L1 content just generated into 600-character segments
            level_2_docs = self._splitter_level_2.create_documents([l1_doc.page_content])
            for l2_doc in level_2_docs:
                l2_id = self._build_chunk_id(2) # Issue L2 its ID

                # [Level 3 - micro tier] Split the L2 content into 300-character sentences
                level_3_docs = self._splitter_level_3.create_documents([l2_doc.page_content])
                for l3_doc in level_3_docs:
                    # Final packaging — this dict is what actually flows into the store
                    root_chunks.append({
                        "text": l3_doc.page_content,
                        "chunk_id": self._build_chunk_id(3), # Its own ID
                        "parent_chunk_id": l2_id,  # [Foreign key]: who's my parent
                        "root_chunk_id": l1_id,    # [Foreign key]: who's my grandparent
                        "chunk_level": 3,          # I'm tier 3
                    })

Design Highlight: Using an Async Queue to Solve Concurrent Communication

In a standard Python flow, the whole thread blocks while the Agent runs search_knowledge_base. To let the frontend see progress from that underlying tool, like "🔍Rewriting the query...", we use asyncio.Queue:

async def chat_with_agent_stream(user_text, user_id, session_id):
    # Unified output channel: both model tokens and low-level tool status land here
    output_queue = asyncio.Queue()

    # This proxy class is placed in the global scope so deep LangGraph execution can push progress into the queue in real time
    class _RagStepProxy:
        def put_nowait(self, step):
            output_queue.put_nowait({"type": "rag_step", "step": step})

    # Start a background coroutine to run the brain's reasoning
    async def _agent_worker():
        async for msg in agent.astream(...):
            await output_queue.put({"type": "content", "content": msg})
        await output_queue.put(None) # Completion signal

    asyncio.create_task(_agent_worker())

    # Main loop streams events back to the frontend
    while True:
        event = await output_queue.get()
        if event is None: break
        yield f"data: {json.dumps(event)}\n\n"

🚪 The Tool Gateway & State Escape Hatch (backend/tools.py)

This module acts as the bridge between the LangChain Agent and the LangGraph RAG state machine.

State Escape-Hatch Design

A regular LangChain Tool can only return a plain string to the LLM. But the complex RAG process produces a lot of valuable intermediate logging (rag_trace). Here, the tool extracts a clean text block for the model, while quietly stashing the rag_trace into a global object, waiting for the main loop mentioned earlier to pick it up and forward it to the frontend.
